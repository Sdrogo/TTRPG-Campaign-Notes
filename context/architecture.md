# Architecture Context

## Stack

| Layer     | Technology                          | Role                                                                 |
| --------- | ------------------------------------ | --------------------------------------------------------------------- |
| Frontend  | React + Vite + TypeScript            | SPA UI. Talks to the backend API only — never queries Supabase directly for domain data (see Auth and Access Model). |
| Backend   | Python + FastAPI                     | Sole writer/reader of domain data. Owns authorization, visibility filtering, ownership rules, the Reveal action, audit logging, and the Agent export/API. |
| Database  | Supabase (PostgreSQL)                | Persistent storage for all domain metadata — Rooms, Memberships, Documents, Tags, Threads/Posts, Glossary, Invitations, AuditLog. |
| Auth      | Supabase Auth (OAuth: Google, Discord, Facebook, GitHub, X) | Identity and session issuance (D-07; Google preferred). Backend verifies the Supabase JWT on every request; it does not manage passwords or OAuth itself. |
| File Storage | Supabase Storage                  | Document images, Comment images, avatars and PDF Attachments (D-09, FR-D1, D-21), in a **private** bucket. Only the file path is stored in Postgres; the backend hands out short-lived signed links. |

## System Boundaries

**Two codebases**, each with its own repo/folder:

- `frontend/` — React SPA (its routed pages include the Room **setup page**, `/rooms/:roomId/setup`, reachable only by an Administrator of that Room — member management, the Main Tags, the Tag list with its delete buttons and the Room's deletion (spec 13) — which replaced the old members page; `/rooms/:roomId/members` redirects there). Renders UI, manages client‑side Supabase Auth session (login, token refresh, logout), and calls the backend API for everything else (Rooms, Documents, Threads, Tags, Glossary, visibility, invites, export). It never reads or writes Postgres or Storage directly.
- `backend/app/api/` — FastAPI route handlers, one module per resource (`account` — the caller's own profile —, `rooms`, `documents`, `comments` — the first slice of `threads` —, `notes`, `document_files` — PDF Attachments —, `tags`, `glossary`, `visibility`, `invitations`, `export`, and `friends`, the first not scoped to a Room). Routes parse/validate input and call the domain layer; they contain no business rules themselves. Membership, "is this Document visible to the requester", "may they manage it" (`get_owned_document`, D-12) and "which of its images may they see" checks shared by nested routers live in `app/api/access.py`, so every router under a Document applies them identically; the shared image upload pipeline lives in `app/api/image_uploads.py` (used by Document images, Comment images and avatars); the profile fields every response that names a user carries live in `app/api/profiles.py`.
- `backend/app/domain/` — Framework‑independent business logic: role checks, Ownership rules (D-03, D-12), visibility filtering (VR-01…VR-11), the Reveal action, the reply‑visibility constraint (D-17), Administrator/Master succession rules (D-16). This is where every invariant in this document is enforced, and it is what a test can exercise without spinning up FastAPI or a real database.
- `backend/app/db/` — Data access layer: Postgres queries/repositories and Supabase Storage calls. No business rules here — only reads/writes, shaped by what the domain layer asks for.
- `backend/app/auth/` — Verifies the Supabase‑issued JWT on incoming requests and resolves it to an internal user id + active Room membership.
- `context/` — This spec/context folder, shared reference for both codebases and for any Agent (not part of either app's build).

## Storage Model

- **Database (Supabase Postgres)**: all metadata and relationships — Users (mirrored from Supabase Auth), Rooms, Memberships (role: Master/Player, Administrator flag), Documents (name, description, Tags, Owner refs, image *reference*), Notes, Tags, GlossaryEntries, Threads/Posts (Comments and Details), Invitations, VisibilityRule, AuditLog.
  - The `Users` mirror is intentionally minimal (`id`, `email`) and kept in sync **opportunistically, not via a dedicated sync job**: whenever a request creates a Room or accepts an Invitation, the backend upserts a row for the acting user from their already-verified JWT claims (`app/db/users_repo.py`); a token without an email claim never overwrites a stored email with NULL. This is enough to show a human-readable identity in the members list (built for UC-05) without a webhook or scheduled job; a user who has never created/joined a Room simply has no row yet, which is fine since they can't be a `Membership.user_id` in that case either. Members who joined *before* the mirror existed had no row (the UI showed their raw id); migration `d3e8a1f4c2b7` backfilled their emails once from `auth.users` (2026-09-21). The frontend never shows a raw user id as a name: a member with no email renders as the unknown-user label ("Utente sconosciuto" / "Unknown user", `frontend/src/lib/members.ts::unknownUserLabel`). The one exception is picker options (Owner, Selective grants), where the fallback adds the first 8 characters of the user id (`memberOptionLabel`). Otherwise two members without an email would look identical, and access could be given to the wrong one.
- **User profiles** (2026-09-22, migration `7a4d2c9e1b58`, spec `context/feature/05 - Account Page.md`): the `users` mirror also holds the profile the user edits on the Account page — `display_name` (≤60), `pronouns` (≤40), `bio` (≤1000), `avatar_path`. Rules (trim, collapse whitespace in single-line fields, blank = unset, length limits) live in `app/domain/profiles.py`. `/account` routes act on the caller only (no user id in the path), so nobody can edit another user's profile; a write first upserts the caller's mirror row, so a user who never joined a Room can still set up a profile. The members list returns the profile fields (`display_name`, `pronouns`, `bio`, `avatar_url`, plus the existing `email`) for every member, and the frontend names users with `display_name ?? email ?? unknownUserLabel()` (`frontend/src/lib/members.ts::userDisplayName`). Profile fields are shown to members of the Rooms the user shares — the same audience that already saw their email.
  - **Google defaults** (2026-09-22, migration `b2e6f1a8c4d9`; since spec 08 they apply to every provider, though the code keeps the `google_` names): `app/auth/` also reads the name and picture Supabase puts in the token's `user_metadata` (`full_name`/`name`, falling back to the `user_name`/`preferred_username` handle GitHub and X send when there's no name; `avatar_url`/`picture`). The first `GET /account` for a user with no `users.profile_prefilled_at` copies them in — the name only if `display_name` is unset (cut to the limit, not rejected), the picture only if there's no avatar, imported through the normal avatar pipeline at 512px (Google's `=s96-c` size option is rewritten) — then sets the marker under the row lock, so it happens exactly once. After that the profile is entirely the user's. A picture that can't be fetched is logged and skipped; the name is still copied. Users who existed before this was added get it on their next visit. `/auth/me` still returns only `id` + `email`.
  - **Avatars** go through the same image pipeline as Document images (validate by content → normalize → WebP), but `normalize_image(..., square=True)` center-crops to a square and caps it at 512px (`AVATAR_DIMENSION`). They're stored in the same bucket under `avatars/{user_id}/{random uuid}.webp` — a fresh name per upload, so a replaced avatar never serves a stale cached copy. Changing or removing an avatar locks the user's row (`SELECT … FOR UPDATE`), confirms the new object and schedules the old one for removal in the same transaction, using the `storage_cleanup` mechanism below; the sweep treats a path referenced by `users.avatar_path` as in use, exactly like one referenced by `document_images`.
- **The Documents list is read in a fixed number of queries** (2026-09-23, spec 07): `GET /rooms/{id}/documents` feeds `DocumentCard`, which now renders each Document's Tags, images and Owners, so it used to cost ~6 round trips per Document (owners, grants, tags, images, plus two for the Comment-visibility filter). It now batches: one query each for owners and Selective grants across the Room, the visibility filter, then one query each for the tags and images of the Documents that survived it, and two for the Comment filter — `documents_repo.*_for_documents` and `api/access.py::get_visible_images_for_documents`. Tags and images are deliberately read **after** the filter, so nothing is fetched for a Document the viewer can't see. The batched image path reuses the same `visible_document_images` filter as the single-Document one (Invariant 1); `tests/test_documents_api.py` pins that a Private Comment's attachment never reaches another member's list response.
- **Main Tags** (2026-09-30, spec `context/feature/11 - Add Room Menagment Page.md`, migration `a7c3e9d1b254`): a Room's Main Tags are the Tags its Documents list groups by, and **an Administrator chooses which Tags they are and in what order**. Stored as `tags.main_position` (nullable integer: NULL = not a Main Tag, otherwise ascending order). This replaces spec 10's implicit rule "a Tag with category `Type` is a Main Tag" (`category` is now only a label; the migration promoted every existing `Type` Tag, ordered by name within its Room, so nothing changed on screen). New Rooms seed the default Tags as Main Tags in `DEFAULT_TAGS` order (NPC, PC, Place, Event, Artifact); a Tag created later is not a Main Tag until an Administrator adds it. `PUT /rooms/{id}/tags/main` (Administrator only, `is_admin` — the Master alone isn't enough) takes `{tag_ids: [...]}` and **replaces the whole selection**: listed Tags get their index, every other Tag of the Room gets NULL. The rule lives in `app/domain/tags.py::plan_main_tags` (no duplicates, every id must be one of the Room's Tags, both 422) and the write only touches rows of that Room. Positions are rewritten together, so there is no uniqueness constraint and gaps are harmless. It isn't AuditLogged: Invariant 7 lists visibility, Reveal, role and Ownership changes, and ordering Tags is none of them. Every Tag response carries `main_position`.
- **Tag combinations** (2026-10-01, spec `11_2 - Add Room Setup Page Refinment.md`, migration `b5d8f2a9c1e3`): the Documents list can also group by a **combination of two or more Tags**. The Room's grouping is an ordered list of *Main items*: an item with one Tag is a Main Tag (`tags.main_position`, spec 11), one with two or more is a combination (`tag_combinations`: `id`, `room_id`, `position`; its Tags in `tag_combination_tags`). Both kinds **share one numbering** (`main_position` and `tag_combinations.position` are indexes in the same list), so they interleave freely and sorting by position gives the order. A Document belongs to a combination when it carries **all** its Tags (AND, like the Tag filter) and, as before, appears in every item it matches, so it can sit under a combination and under its single Tags. A Tag may be a single item and part of any number of combinations. The API moved to `app/api/main_items.py`: `GET /rooms/{id}/tags/main` (any member; the Documents list needs it) returns the items in order, `PUT` (Administrator only) replaces them all with `{items: [{tag_ids: [...]}]}` — 422 for an empty item, a repeated single Tag, a repeated Tag inside a combination, the same set of Tags twice (in any order) or a Tag outside the Room (`app/domain/tags.py::plan_main_items`, `ordered_main_items`). It replaces the spec 11 body `{tag_ids}` and its Tag-list response. The client grouping is `frontend/src/lib/documentGrouping.ts::groupDocumentsByMainItems`; an item that refers to a missing Tag is ignored whole, never shown as a partial combination. Both tables are backend-only (RLS + deny policy, like every table). Not AuditLogged, like the Main Tags.
- **Notes** (2026-10-01, spec `12_1 - Note backend effort.md`, migration `c6e1a4b7d2f9`): a Document can carry Notes, extra blocks with a `title` (≤200), a `description` (plain text with the same `#Name` mentions as a Document description, no length rule, like that one) and **a visibility of their own**. Tables `document_notes` (`position` orders them) and `document_note_visibility_grants`, both `ON DELETE CASCADE` from the Document — a Note holds no Storage object, so nothing needs `storage_cleanup` — both backend-only (RLS + deny policy). **A Note is the Detail of D-18** ("an additional titled Description"), under the product's own name for it (decided 2026-10-01). It **deliberately departs from D-19/I-10/FR-T10**, which describe a Detail as a Post in the Thread that any member may add, only its author or the Master may edit, and that carries nested replies: here a Note lives in its own table, is managed by the Document's Owners and the Master, and has no replies. The departure is logged as an Open Question, since `requirements.md` is protected.
  - **Visibility** reuses the Document levels through `app/domain/visibility.py::is_note_visible` → `is_content_visible`, with the **Document's Owners as the "Owner"**: Room = everyone who sees the Document, Master = Masters, Private = the Document's Owners + Master, Selective = those + the grant list. A Note is only reachable through a Document the viewer already sees (hidden Document → 404 for its Notes). **A Note the viewer can't read is absent from every response** — no placeholder, no count — and a request for it is **404, not 403**, same as a Note that doesn't exist (`routes` look the Note up among the viewer's *visible* Notes, and check visibility before permission so the status can't reveal a hidden one). As with a Document, an Owner who sets a Note to "Master" no longer sees it.
  - **Permissions** (`app/domain/notes.py::can_manage_notes`): Owners and the Master create, edit, delete, reorder and change visibility (D-12, same rule as the Document description); nobody else. Each Note carries `can_edit`/`can_delete`. `selective_user_ids` is sent only to those who can manage the Note — a reader sees the level, not who else was let in. A visibility-level or grant-list change writes a `note_visibility_changed` AuditLog row in the same transaction (Invariant 7); text edits, creation and deletion are not audited (like Comments).
  - **Where they are returned**: `GET/POST/PATCH/DELETE /rooms/{id}/documents/{doc}/notes` (`app/api/notes.py`) and **embedded as `notes` in every single-Document response** (`DocumentDetailResponse`: GET one, create, PATCH, image and Owner routes), so the detail page needs no second request and a cache updated from any of those responses can't lose its Notes. **Not in the Documents list**: a card doesn't show them and that path stays at a fixed number of queries. Read through `app/api/access.py::get_document_notes` (two queries whatever the count, filtered once for every route).
  - **Limits and order**: ≤50 Notes per Document (409 beyond), counted over *all* of them including ones hidden from the creator. New Notes go after the highest `position`. Create and reorder take the Document's row lock before reading, so concurrent creates can't overshoot the cap or share a position. `PUT .../notes/order` takes `{note_ids}` = exactly the Notes the requester sees (422 otherwise, repeats included); a Note hidden from them **keeps its own slot** and the visible ones are dealt into the rest (`plan_note_order`), so ordering neither needs nor reveals a hidden Note's id.
- **PDF Attachments** (2026-10-01, spec `16 - PDF attachments on Documents.md`, D-21, D-22, VR-12, FR-D8, migration `e2f7c4a9b1d6`): a Document can carry PDF files, typically a PC's character sheet. Table `document_files` (`storage_path`, `display_name`, `size_bytes`, `content_type`, `uploaded_by`, `created_at`; `ON DELETE CASCADE` from the Document; backend-only, RLS + deny policy). **An Attachment has no visibility of its own**: it is only reached through a Document the viewer already sees (hidden Document → 404), and everyone who sees the Document sees its files (VR-12). A secret file goes on a secret Document.
  - **Rules** (`app/domain/files.py`): accepted **by content**, the bytes must start with `%PDF-` (422 otherwise, whatever the name); ≤10 MB (413, read one byte past the cap, like images); ≤10 per Document (409), counted under the Document's row lock so concurrent uploads can't overshoot. **Not re-encoded**: stored as uploaded. The display name is the uploaded file's name without directory parts or control characters, whitespace collapsed, cut (not refused) to 200 characters keeping a `.pdf` ending, `document.pdf` when empty. The object name is random: `documents/{document_id}/files/{uuid}.pdf`, in the same private bucket.
  - **Who**: Owners and the Master upload and remove (D-22, through `access.get_owned_document`: 404 before 403, so the status can't reveal a hidden Document). Each file carries `can_delete` so the UI doesn't re-derive it. Not AuditLogged (no visibility, role or Ownership change), like images.
  - **Serving**: a PDF can carry scripts, so it is **never rendered from the app's origin**. Each file's `url` is the usual cached 1-hour signed link plus Supabase's `download=<name>` parameter (`storage.as_download`), so Storage answers with `Content-Disposition: attachment` and the stored `application/pdf` type. The frontend opens it in the browser's viewer through a blob URL or offers a plain download (spec 16_2).
  - **Routes** (`app/api/document_files.py`): `POST /rooms/{id}/documents/{doc}/files` (multipart, returns the new file) and `DELETE .../files/{file}` (204). Files are **embedded as `files` in every single-Document response** (`DocumentDetailResponse`), like Notes, and **not in the Documents list**, which keeps its fixed number of queries.
  - **Storage consistency**: the same `storage_cleanup` mechanism as images. Upload: cleanup row committed first, object uploaded, link signed, then the row inserted and the cleanup row cleared in the request's transaction (a link Storage can't sign is a 502 and leaves the object to the sweep). Removal: `document_files.remove_files` deletes rows and schedules the objects for after commit. The sweep treats a path in `document_files.storage_path` as in use.
- **Characters** (2026-10-01, spec `17 - Characters and posting in character.md`, D-23 to D-25, VR-13, FR-D9, FR-T11, I-13, migration `a3d9c5e7f210`): a Document becomes a Character through a relation, not a type (D-05). Only columns are added, so RLS is unchanged.
  - **Storage**: `documents.played_by` (nullable user id, no FK like every user reference) is the one member who plays it (D-23); `posts.as_document_id` (nullable FK to `documents`, `ON DELETE SET NULL`, indexed) is the Character a Comment is written as. Deleting the Character turns its Comments back into plain ones, which shows the real author and so widens nothing. When a member leaves or is removed, `rooms.remove_member` clears every `played_by` pointing at them in the same transaction (D-15: the Documents stay); Comments they already wrote as a Character keep it.
  - **Linking** (`PUT /rooms/{id}/documents/{doc}/player`, `{user_id | null, add_as_owner = true}`): Owners and the Master (D-12, via `access.get_owned_document`, 404 before 403). The player must be a member (422). `add_as_owner` also inserts an Owner row unless they already own it. A real change of player writes `character_player_changed` and an added Owner writes `document_owner_added` to the AuditLog, in the same transaction (Invariant 7); re-sending the same player writes nothing. Rules in `app/domain/characters.py::plan_player_change`. Every Document response (list included, the column is free) carries `played_by` as a bare user id, like `owner_ids`: the client resolves the profile through the members list, which always contains the player since leaving clears the link. (The ticket suggested embedding profile fields; a bare id keeps the list at its fixed query count.)
  - **Writing as a Character** (D-24, UC-22): Comment create and PATCH accept `as_document_id` (PATCH: sending `null` drops it, omitting it keeps it). The Document must be in the Room and visible to the author (404 otherwise, VR-07), then `can_post_as` decides (403): its player, or the Master for any Document (NPCs). PATCH re-checks only a *new* Character, so an unlinked player can still edit a Comment's text. The Post stays the author's: edit, delete and visibility rules are unchanged, and switching Character isn't audited.
  - **Reading** (VR-13, I-13): `CommentResponse.as_character` (`{document_id, name, image_url}`) is filled **only when the viewer sees that Document**; otherwise it is null and the real author shows. `api/characters.py::visible_characters` reads every Character of a Comments list in a fixed number of queries (Documents, Owners, grants, the visibility filter, then their visible images, one signing request). The image is the first one the viewer may see in gallery order, as on the Document's card.
  - **Picker**: `GET /rooms/{id}/characters/mine` lists what the caller may write as, by name: the Documents they play and can see, or every Document for the Master. Empty means the composer hides the selector.
  - **Frontend** (spec 17_2): `useMyCharacters` feeds the composer's "Post as" picker; the last choice is remembered per Room in `localStorage` (`lib/characters.ts`, convenience only, ignored if no longer allowed). An edit sends `as_document_id` only when the choice changed, so an unlinked player can still fix a Comment's text. `useSetDocumentPlayer` reloads the Document, the list and the caller's Characters.
- **Threads/Posts**: there is **no `threads` table** — a Document has exactly one Thread (D-20/I-11), so a Post (`posts` table) points straight at its Document. `posts.kind` is `comment`; Details (D-18) are implemented as Notes (see above), not as Posts. Per-Post Selective grants live in `post_visibility_grants`. A deleted Comment keeps its row (body emptied, `deleted_at` set) so the conversation keeps a placeholder (FR-T5). Added 2026-09-21 (migration `2393196bb425`).
  - **Comment visibility** reuses the Document levels through `app/domain/visibility.py::is_content_visible`, with the author as the "Owner". A Comment is only reachable through a Document the viewer already sees (hidden Document → 404 for its Comments too), and **the author always sees their own Comment**, even at "Master only" (VR-02). A visibility or grant-list change writes a `comment_visibility_changed` AuditLog row in the same transaction (Invariant 7).
  - **Comment images** (2026-09-21, migration `9e29c43313a1`): an image attached to a Comment is stored as a normal Document image (`document_images` row, same bucket/pipeline) with `post_id` pointing at the Comment, so it appears both on the Comment and in the Document's gallery. **It inherits the Comment's visibility**: every Document response filters its `images` per viewer through `app/domain/visibility.py::visible_document_images` (via `app/api/access.py::get_visible_images`), so a Private Comment's image never reaches the gallery of someone who can't read the Comment (Invariant 1). The FK is `ON DELETE CASCADE`, not `SET NULL` — unlinking would silently widen a private image to the whole Document audience. Attaching/removing is author-only (like editing), max 4 per Comment (`MAX_IMAGES_PER_COMMENT`), and they count toward the Document's 20-image cap. Deleting a Comment also deletes its images (rows now, Storage objects after commit, see below); a Document Owner/Master can still remove any image *they can see* from the gallery. The upload pipeline (normalize → plan → upload → record, with rollback on failure) lives in `app/api/image_uploads.py`, shared by the Document and Comment image routes.
  - **Permissions**: only the author edits a Comment (the Master does *not* get implicit edit rights, unlike Documents' D-12); the author or the Master can delete one (moderation, section 9 matrix). The API returns `can_edit`/`can_delete` per Comment so the UI never re-derives these rules.
- **Mentions** (2026-09-22, specs `context/feature/06 - Quick navigation.md` and `06_1 - Quick navigation refnment.md`, first slice of FR-D4): stored as **plain text** inside a Document description or Comment body, `#Name` — no table, no ids, no backend change. `#Name` refers to a Document or a Tag. The frontend resolves them at render time against the Room's Document list (which the backend already filters per viewer) and Tag list (`frontend/src/lib/documentMentions.ts::splitMentions`: longest name wins, a Document wins over a Tag with the same name), so a mention of a Document the viewer can't see is shown as plain text and never reveals the target (VR-07). A Tag mention links to the Documents list filtered by that Tag (`/rooms/{id}/documents?tag={tagId}`, filtered in the browser over the already visibility-filtered list, FR-N2). The mention popup can also **create** the typed name as a new Tag (`POST /rooms/{id}/tags`, Master/Administrator only) or a blank Document (`POST /rooms/{id}/documents` with only `name`, so it gets the backend default **Room** visibility — the user's choice, 2026-09-22; D-13 applies). The UI only offers what the backend would allow (`frontend/src/lib/roomPermissions.ts`). Trade-offs, accepted for now: renaming a Document or Tag breaks existing mentions of it, two Documents with the same name resolve to the first one, and there are no backlinks yet (those will need the mentions stored server-side, see Open items).
- **File/Blob Storage (Supabase Storage)**: Document images and other uploaded media. The backend authorizes an upload (checking the user is an Owner of the target Document, D-12); the client never talks to Storage and never holds a bucket key.
  - **Document images** (bucket `document-images`, table `document_images`, many per Document) are **proxied through the backend**, not uploaded client-side with a signed URL: the client sends either the file (`POST .../images`, multipart) or a URL (`POST .../images/from-url`), and the backend validates the bytes are a real PNG/JPEG/WebP/GIF (Pillow, by content, not filename), downscales to ≤1920px on the longest side, re-encodes to WebP (which also strips EXIF/GPS metadata), then uploads with its secret key. Chosen over the signed-upload-URL flow because URL imports have to be fetched and resized server-side anyway, and one server-side pipeline means the size/format rules can't be bypassed by a modified client. Replaced the earlier single-`image_path`-column draft (never shipped) on 2026-09-21.
  - **URL imports are an SSRF surface**: `app/db/remote_images.py` only allows http(s) to publicly routable addresses (re-checked on every redirect hop, max 3), with a timeout and a 20 MB streaming cap. **DNS rebinding is prevented** (2026-09-22): each hop's host is resolved once, every returned address must be public, and the connection is then pinned to the validated IP — the original name goes in the `Host` header and, for HTTPS, as the TLS SNI name, which httpcore also verifies the certificate against. httpx never resolves the host a second time.
  - **Keeping Storage and its referencing rows in step** (`document_images.storage_path`, since 2026-09-22 `users.avatar_path`, and since 2026-10-01 `document_files.storage_path`) (2026-09-22, migration `5c1f7e2a9b30`, `app/db/storage_cleanup.py`): Storage isn't part of the Postgres transaction, so every object that might end up unreferenced gets a `storage_cleanup` row first. On upload, the row is committed in its own transaction *before* the object is uploaded and deleted in the request's transaction together with the image row insert — if that transaction never commits, the row stays behind. On delete, the image rows are deleted and cleanup rows inserted in the request's transaction, and the objects are removed only **after** it commits (`app/db/session.py::on_commit`), so a rollback leaves both rows and objects intact. A background sweep (started from `app/main.py`'s lifespan, every 10 minutes) retries every cleanup row older than 15 minutes, which covers both orphaned uploads and removals that failed because Storage was down. Removal is idempotent, and an object is never removed while an image row still references its path. Deleting an image therefore no longer returns 502 when Storage is down; the removal is just delayed.
  - **The favorite image** (2026-09-23, migration `a4f7b2c8e015`, spec `context/feature/07 - Document visualizazion refactor_beckend.md`): `document_images.is_favorite` marks the one image that leads a Document — first in its gallery, and so the one a `DocumentCard` shows. "Only one per Document" is enforced by the database, with a partial unique index (`uq_document_images_one_favorite` on `document_id WHERE is_favorite`), not just by the route: two concurrent `PUT .../images/{id}/favorite` calls would otherwise both leave their flag set. The rules live in `app/domain/documents.py`: the first image added to a Document claims the flag (`plan_new_image`), and removing the favorite hands it to the oldest survivor (`next_favorite_id`, applied in `image_uploads.py::remove_images`), so **a Document that has images always has exactly one favorite**. Setting it is Owner/Master-only (D-12) and restricted to an image the requester can already *see*, exactly like deleting one — otherwise an Owner could probe for a Private Comment's attachment by trying ids (VR-07). A Comment attachment may be the favorite; it stays visibility-filtered, so a viewer who can't read that Comment simply gets the next image leading their card (Invariant 1). Ordering (`is_favorite DESC, created_at, id`) lives in `documents_repo`, so every read path agrees on which image is first. **Every write that depends on which images a Document currently has takes the Document's row lock first** — the upload paths already did, and so now do setting the favorite (locked in the route *before* the visibility read, so the check and the write are one step) and removing images (locked before the delete, covering the delete, the read of what survived and the promotion, for *every* affected Document and in sorted id order). Without it two concurrent favorite moves collide on the unique index and one request dies, and a concurrent delete of the image another request is about to promote leaves the Document with images and no favorite — which the index cannot catch, since it only forbids a second `true`. The promotion is likewise **decided from a read taken under the lock**, never from an `is_favorite` read before it: whether a Document needs a successor is asked of every affected Document after the delete, because a stale flag saying "not the favorite" would skip the promotion silently.
  - **Image limits are enforced under a lock**: `ensure_room_for_another_image` takes a `SELECT … FOR UPDATE` on the Document row, held until the request's transaction ends, before counting. Concurrent uploads to the same Document (and Comment attachments, whose per-Comment count is taken after the lock) are serialized, so they can't overshoot the 20-per-Document / 4-per-Comment caps.
  - **Deleting a Document** (2026-09-25, `DELETE /rooms/{id}/documents/{doc}`, spec `10 - UX Refinment.md`, Owner/Master only, D-12): its Tags, Owner and Selective-grant links and its Comments (`posts`, `post_visibility_grants`) cascade at the database level (`ondelete="CASCADE"`). Its images do **not** — a plain cascade would delete the `document_images` rows without ever queuing their Storage objects, orphaning them forever, since nothing else would create the `storage_cleanup` row that removal depends on. The route locks the Document, reads every image it has (Comment attachments included — `documents_repo.list_images` doesn't filter by visibility, since deleting the Document doesn't need to), and runs them through `image_uploads.remove_images` (the same path a manual gallery deletion uses) *before* deleting the Document row, so Storage stays consistent with the same guarantees as any other image removal. Its PDF Attachments (spec 16) go the same way, through `document_files.remove_files`.
  - **Deleting a Room** (2026-10-01, `DELETE /rooms/{id}`, spec `13_1`, **Administrator only** - `is_admin`, the Master alone isn't enough; 403 for a non-member like the other Room routes): the Room row's database cascades take Memberships, Invitations, Tags, Tag combinations, Documents (and under them Owners, grants, Notes, Comments, Document-Tag links) and **the Room's own `audit_log` rows** - nothing about the deletion is kept, and Invariant 7 doesn't list it. Images are the same trap as for a Document: the cascade would drop the `document_images` rows without queuing their Storage objects. The route first row-locks every Document of the Room (id order, `documents_repo.lock_documents_for_room`), reads all their images (Comment attachments included, unfiltered - deleting needs no visibility check) and runs them through `image_uploads.remove_images`, and all their PDF Attachments through `document_files.remove_files`, then deletes the Room; the objects go after commit.
  - **Deleting a Tag** (`DELETE /rooms/{id}/tags/{tag}`, spec `13_1`): Administrator **or Master**, the same people who may create one (403 otherwise, 404 for a Tag that isn't in this Room). `document_tags` and `tag_combination_tags` rows cascade; Documents keep everything else. The Tag's own single Main item goes with its `main_position`. Combinations are rewritten by `app/domain/tags.py::plan_tag_removal`: one that held the Tag shrinks, one left with fewer than two Tags is dropped (a one-Tag combination would repeat a Main Tag item, which `plan_main_items` refuses), and a shrunken one equal to another keeps only the earlier position. The route takes the Room's row lock (`rooms_repo.lock_room`), which `PUT /tags/main` now takes too, so a deletion and a Main items save can't interleave. `#TagName` mentions of the deleted Tag stop resolving and render as plain text (the accepted trade-off under Mentions); no text is rewritten.
  - **The bucket is private** (since 2026-09-22; it used to be public). Every image URL in a response — Document and Comment images, avatars — is a **signed link valid for 1 hour**, created by `app/db/storage.py::signed_urls` only for images that response may show (they've already been through the visibility filter, Invariant 1). Each response signs its images in **one** Storage request (`sign_images` / `sign_avatars`; the Document list collects every visible image first). Links are cached in-process and reused while at least 15 minutes remain, so an image keeps the same URL across requests and stays in the browser cache. A removed object's link is dropped from the cache when its removal is scheduled. If Storage can't sign, the response still succeeds: the image is left out and an avatar falls back to initials. What's left of the old caveat: a link someone already has keeps working until it expires (≤1 hour), and URLs from the public-bucket era may still be served from Supabase's CDN cache until it expires (confirmed live: a never-fetched object's public URL is refused, while an already cached one still loaded right after the switch).

## Not Room-scoped: Friendships

Added 2026-10-02, spec `context/feature/18 - Friends.md` (D-26, D-27, FR-F1 to FR-F4), unit 18_1a, migration `b7e1d4f8a2c6`. Everything else in this document hangs off a Room (D-06); a Friendship links two users directly, so it gets its own rules here.

- **Storage**: `friendships` (`user_low`, `user_high`, `requested_by`, `status` pending | accepted | declined, `created_at`, `responded_at`, `hidden_from_sender`) holds **one row per pair**: the ids are stored ordered (`CHECK user_low < user_high`, unique together), so a request can't be duplicated in either direction. `friend_codes` holds one code per user (`user_id` primary key, `code` unique). Both backend-only (RLS + deny policy). No Room FK: nothing about a Friendship cascades from a Room, and leaving or deleting a Room doesn't touch it.
- **Rules** (`app/domain/friends.py`): a request by `user_id` needs the two users to **share a Room at request time**, a request by `code` doesn't (D-27; no search by name or email). Only the recipient accepts or declines. Either Friend removes the Friendship and the sender cancels a pending request; both delete the row. The recipient of a pending request can't remove it, only answer it (409), so a decline always starts the cooldown.
- **Silent decline and the cooldown** (D-27): a declined row is kept with `responded_at` as the decline time. The sender keeps seeing it as an outgoing request (`view_for`); re-sending it answers "already sent", exactly like a pending one. Cancelling it doesn't delete it (that would end the cooldown) but sets `hidden_from_sender`, and re-sending after that quietly un-hides it (201, nobody is asked). The user who declined no longer sees the row and gets 409 if they ask within 30 days. After 30 days either user may ask: the same row is reused with the new sender, `created_at` reset and `responded_at` cleared. (`hidden_from_sender` is not in the ticket's table: it is what "the sender sees pending until they cancel" needs without losing the cooldown.)
- **Routes** (`app/api/friends.py`, caller-scoped like `/account`): `GET /friends` (`friends`, `incoming`, `outgoing`), `POST /friends/requests` `{user_id}` or `{code}`, `POST /friends/requests/{friendship_id}/accept` and `/decline`, `DELETE /friends/{user_id}`, `GET /account/friend-code` (created on first use) and `POST /account/friend-code` (regenerate; the old code stops working at once).
- **Privacy** (NFR-03): an entry carries the same profile fields as a members list (`api/profiles.py`), but **the email is null unless the two users share a Room right now**, the audience that already saw it. Read in a fixed number of queries (rows, profiles, shared Rooms, one signing request).
- **Races**: a request takes a transaction-scoped advisory lock on the pair (`friends_repo.lock_pair`) before reading, since the row may not exist yet; answers and removals lock the row. Two concurrent first visits to the Friend code agree on one (`INSERT … ON CONFLICT DO NOTHING`, then read).
- Not AuditLogged: Invariant 7 lists Room-scoped changes, and a Friendship belongs to no Room.
- **Direct Room invitations** (2026-10-02, unit 18_1b, FR-F5, migration `c4f9a2e7d1b8`): `invitations.invitee_user_id` (nullable, indexed) addresses an invitation to one user; NULL is a shareable link, as before. `POST /rooms/{id}/invitations/direct` `{user_id, role}`: Administrator only (403), the target must be an **accepted** Friend of the caller (403, a pending request isn't enough) and not already a member (409); rules in `app/domain/invitations.py::plan_direct_invitation`. It has the usual code and 7-day expiry, and a new one to the same Friend for the same Room revokes the one still open (the latest role wins; taken under the Room's row lock). **It never makes anyone a member**: the Friend joins only through the existing `POST /invitations/{code}/accept` (FR-R3), which now answers 404 to anyone but the invitee (`check_invitation_for`), even if they learn the code. `GET /invitations/mine` lists the caller's direct invitations they can still accept (not revoked or expired, for a Room they aren't in), with the Room and the sender's profile under the Friend rule (email only while they share a Room). `POST /invitations/{code}/decline` (204) lets the invitee turn it down: it is revoked, leaves their list and its code stops working, silently for the sender, who may invite again. Only the invitee can decline, and never a link invitation (that would revoke it for everyone): both answer 404, an expired or revoked one 410 (`plan_decline`). Not audited, like link invitations. Removing the Friendship later doesn't revoke an open invitation.

## Backend Data Access

- The backend connects to the Supabase Postgres instance **directly** — SQLAlchemy 2.0 (async, `postgresql+asyncpg` driver) for queries, Alembic for schema migrations — rather than through Supabase's PostgREST/`supabase-py` client. Decided when building the Rooms/Membership slice (2026‑09‑21). (`asyncpg` over `psycopg[binary]`'s async mode: the latter cannot run under Windows' default `ProactorEventLoop`, which is what `uvicorn`/`alembic` use on Windows by default — `asyncpg` has no such restriction.)
- Chosen so that a multi‑table write (e.g. creating a Room + its initial Membership + its default Tags, or a role change + its AuditLog row per Invariant 7) commits as one real Postgres transaction. PostgREST has no cross‑table transaction primitive from the client side; the alternative would have been pushing that logic into Postgres functions/RPCs, which would split business logic between Python and SQL and contradict the File Organization rule that `backend/app/domain/` is where every invariant is enforced.
- Connects via Supabase's **Session Pooler** (`aws-0-<region>.pooler.supabase.com:5432`, user `postgres.<project-ref>`), not the Direct Connection host — the direct host only has an IPv6 DNS record, which isn't reachable from every network (confirmed during setup: `db.<project-ref>.supabase.co` resolves only to an AAAA record).
- `backend/app/domain/` stays framework‑independent per `code-standards.md`: it works with plain dataclasses, not SQLAlchemy model instances, and does not itself open a DB session. `backend/app/db/` holds the SQLAlchemy models and the repository functions that turn a domain decision into an atomic write.
- Because RLS is not the primary authorization mechanism (see Auth and Access Model below), the backend's Postgres role (`postgres`, the owner of every app table, so RLS doesn't apply to it) has normal read/write access to its own tables.
- **Every table in `public` is backend-only** (2026-09-22, migration `c9d4e7b1f352`): RLS is enabled with a single **restrictive deny policy** `backend_only_deny_clients` (`FOR ALL TO anon, authenticated USING (false) WITH CHECK (false)`, migration `f1c8a2e6d493`; added because Supabase flags "RLS enabled, no policy" when the intent is only implicit), and the Supabase client roles `anon` and `authenticated` have **no privileges** on any table or sequence, including through `postgres`'s default privileges for future ones. Supabase exposes `public` through its Data API, and the publishable key ships in the frontend bundle. Before this change, anyone holding it could read and write every table directly, bypassing the backend's visibility rules (confirmed live, then closed; the Data API now answers "permission denied"). Default privileges only keep a new table unreachable, they don't enable RLS, so **every migration that creates a table must also `ENABLE ROW LEVEL SECURITY` and create the deny policy**; `tests/test_database_security.py` fails otherwise. It also fails on any *permissive* policy for the client roles. Don't apply dashboard "fix" snippets such as `to authenticated using (true)`: they open a table instead of documenting that it's closed. Nothing outside our migrations should live in `public`: a leftover quickstart trigger (`on_auth_user_created` → `public.handle_new_user`, inserting into a non-existent `public.profiles`, which would have broken new sign-ups) was found and dropped by migration `e5a3b8d2c671`.
- App tables that reference a user (`Room.created_by`, `Membership.user_id`, `Invitation.created_by`, ...) store the id as a plain UUID column with **no database‑level foreign key to Supabase Auth's `auth.users`**. That id always comes from a server‑verified JWT `sub` claim (`backend/app/auth/`), never from unchecked input, so the FK would only guard against a bug this app structurally cannot have — while coupling our migrations to a schema we don't own and blocking integration tests from using synthetic user ids (a real FK rejected them, since Supabase Auth never created a matching row for a self‑signed test token).

## Auth and Access Model

- Every user signs in via **Supabase Auth using OAuth** — Google (the preferred one, D-07, FR-A1), Discord, Facebook, GitHub or X (spec 08, 2026-09-23). The providers are enabled in Supabase's dashboard and listed once in `frontend/src/lib/authProviders.ts` (`x` is Supabase's OAuth 2.0 provider, not the legacy `twitter`); the backend doesn't know or care which one was used, since every provider's session is the same Supabase JWT. An account may come without an email (X can withhold it): `users.email` is nullable, invitations are link-based, and a user without a display name or email is shown with the unknown-user label. The frontend holds the resulting session and attaches it as a Bearer token on every backend request.
- The **backend verifies the Supabase JWT** on each call and resolves it to an internal user id — it is the only component that trusts the token; the frontend never talks to Postgres directly, so Row‑Level Security is not relied on as the primary authorization mechanism (kept as optional defense‑in‑depth, not a substitute for backend checks).
- **CORS**: the backend accepts browser requests from the exact origins in `CORS_ORIGINS` (production, localhost) plus any origin matching `CORS_ORIGIN_REGEX`, which exists for Vercel preview deploys, since each gets a generated hostname. Both are set in Render's dashboard, not the repo. Production uses `https://ttrpg-campaign-notes-[a-z0-9]+-rum11\.vercel\.app`, matched against the whole origin. The part between the project name and the `rum11` scope allows **no hyphens** on purpose: with `[a-z0-9-]+`, another Vercel account whose scope merely ends in `-rum11` could match. The cost is that branch-alias previews (`…-git-<branch>-rum11.vercel.app`) are not allowed; open previews through their commit URL. Since the session travels as a Bearer header rather than a cookie, an allowed origin still can't act as a user without their token, but the pattern is kept exact anyway. `tests/test_cors.py` pins both the allowed and the rejected shapes.
- **Roles are per‑Room** (D-06): Master, Player, and the stackable Administrator role (D-11), all read from the `Membership` row for the (user, room) pair — never assumed globally for a user.
- **Ownership** of a Document determines who can edit its description and reassign its Ownership (D-03, D-12). The Master always has *implicit* Ownership of every Document in their Room, even without an explicit Owner row.
- **Visibility** is a separate axis from role/Ownership: it governs which members can *see* a given Document, block, Post, or Glossary entry (section 8 of `requirements.md`). The Master always sees everything in their Room regardless of visibility (D-01, VR-01).
- Every mutating endpoint checks role/Ownership **before** applying any change; every read endpoint applies the visibility filter **before** returning any content — see Invariants.

## Backend Message Localization

Added 2026-09-25, spec `context/feature/09_1 - Removing hardcoded strings for backend.md`. Every user-facing string an API response carries (an `HTTPException`'s `detail`) is rendered from a resource file for the caller's locale, instead of being a hardcoded English literal. This is independent of the frontend's own UI language (which is documented on the frontend i18n branch, spec 09): the two don't share a mechanism, only the same shape.

- **Resource files**: `backend/app/i18n/locales/en.json` and `it.json`, one nested JSON tree per locale, keys grouped by area (`errors.room.*`, `errors.document.*`, `errors.comment.*`, `errors.image.*`, …) — mirroring `frontend/src/i18n/locales/*.json`'s own structure. `backend/app/i18n/translator.py::translate(key, locale, **params)` looks up the dotted key, falling back to `DEFAULT_LOCALE` ("en") when the locale or the key is missing, and finally to the key itself, so a typo produces an unreadable `detail` rather than a 500. Placeholders are `str.format`-style (`{max}`, `{format}`, …), and a param value starting with `@` is itself translated first — used once, by `app/domain/profiles.py::ProfileFieldTooLongError`, to localize the profile field's name before it's interpolated into the "too long" message.
- **Choosing the locale**: `app/i18n/dependencies.py::get_locale` is a FastAPI dependency (`LocaleDep`) that reads the standard `Accept-Language` header (the frontend's `apiFetch` sets it to the UI language picked from the flag selector, not the browser's locale), picks the caller's highest-quality supported preference (`it-IT` counts as `it`), and falls back to English. Every route handler that can return a translated error takes `locale: LocaleDep`; a handful of shared helpers below route level (`app/api/access.py`, `app/api/image_uploads.py`) take `locale: str` as a plain parameter instead, since FastAPI only injects dependencies at the route level.
- **Domain exceptions carry a key, not a message**: every exception a domain function can raise for a rule violation (`NotOwnerError`, `CommentTooLongError`, `RemoteImageError`, …) subclasses `app/domain/errors.py::DomainError`, which stores a translation `key` and the `**params` to interpolate, instead of a rendered English string. This keeps `app/domain/` free of any i18n dependency (per `code-standards.md`'s framework-independence rule) while still letting the API layer render `detail` correctly — `app/api/errors.py::translated_error(status_code, exc, locale)` does the translation at the one point every route already converts a caught domain exception into an `HTTPException`. A plain check that doesn't go through a domain exception (e.g. "not a member of this room") calls `app/api/errors.py::http_error(status_code, key, locale)` directly. `str(exc)` on a `DomainError` is just its key, which is enough for logs and for tests that only need to assert *which* rule fired (`exc_info.value.key`).
- **Adding a locale**: add `locales/<code>.json` with the same keys and placeholders (checked by `tests/test_i18n.py`, mirroring the frontend's `locales.test.ts`) and add the code to `SUPPORTED_LOCALES`. Nothing else changes — no route or domain exception references a locale by name.
- **Not localized**: the default Tags created with a Room (NPC, Place, Event, Artifact; `app/domain/rooms.py::DEFAULT_TAGS`) are stored data, not UI text, same as a Document's name or a Comment's body — out of scope here, same as on the frontend.
## UI Language (frontend)

Added 2026-09-24, spec `context/feature/09 - Removing Hardcoded strings, implement multi lenguage`. The UI is available in **Italian and English**. This covers the frontend only; the backend is a separate task (see below).

- **Every UI string is in a resource file**: `frontend/src/i18n/locales/it.json` and `en.json`, one nested JSON tree per language, grouped by area (`common`, `account`, `documents`, `comments`, `mentions`, …). Components read them with `react-i18next`'s `useTranslation()`. Plain helpers that produce text outside React (`userDisplayName`, `tooLong`, `formatRelativeTime`, the image-error messages in `useComments`) call the shared `i18n` instance directly. There are no string literals for UI text in components. The only literals left are brand names (the sign-in providers in `lib/authProviders.ts`).
- **Keys are type-checked**: `src/i18n/i18next.d.ts` types `t()` against `it.json`, so a mistyped or missing key fails `tsc`. `src/i18n/locales.test.ts` checks that every other language has exactly the same keys and the same `{{placeholders}}`, and no empty string. Plurals use i18next's `_one`/`_other` suffixes and follow each language's plural rules (`Intl.PluralRules`).
- **Choosing the language** (`src/i18n/index.ts::detectLanguage`): a language picked from the flag selector wins, stored in `localStorage` under `ttrpg.language`. Otherwise the first of the browser's `navigator.languages` that we support is used (`it-IT` counts as `it`), falling back to **English**. Only an explicit pick is stored, so until then the app keeps following the browser locale. Storage errors (private mode, blocked site data) are swallowed; the pick then just isn't remembered. `<html lang>` follows the current language.
- **Switching needs no reload**: `setLanguage` changes i18next's language. `App` subscribes to it with `useTranslation()`, so the whole routed tree re-renders, including components that only call the plain helpers. Dates and relative times (`lib/time.ts`) and mention sorting (`lib/documentMentions.ts`) use the current language's `Intl` formatters rather than a fixed `'it'`.
- **Bundled, not lazy-loaded**: both JSON files ship in the main bundle (`initAsync: false`), so the first render already has its strings. That adds about 26 kB gzipped with i18next. Lazy-loading per language (`i18next-http-backend` or dynamic `import()`) is an option once there are more languages.
- **Adding a language**: add `locales/<code>.json` with the same keys, add it to `SUPPORTED_LANGUAGES` and the `resources` in `i18n/index.ts`, and add its flag to `LANGUAGE_FLAGS` (`i18n/languages.ts`, SVG in `src/assets/flags/`). Nothing else changes.
- **Backend text**: error messages (`ApiError.message`, the FastAPI `detail` shown by `notifyError`) are translated by the backend into the locale `apiFetch` sends as `Accept-Language` (see Choosing the locale); the frontend shows them as they come and doesn't map them to its own keys. User content (Document names, descriptions, Comments, default Tag names created with a Room) is data and is never translated.

## Continuous Integration

`.github/workflows/ci.yml` runs on every pull request and on pushes to `main` and `staging` (PRs target `staging`, see `code-standards.md` → Branches and Pull Requests), as two independent jobs matching the two codebases.

- **Frontend**: `npm ci`, `npm run lint`, `npm run build` (which type-checks), then `npm run test:coverage`. The coverage bar lives in `frontend/vitest.config.ts`, not in the workflow, so it is versioned with the code it measures and the same command gates locally and in CI.
- **Backend**: `ruff check` (which also fails on a public module, class or function in `app/` without a docstring — pydocstyle `D1`, see `code-standards.md` → Documentation), `mypy app tests`, then `alembic upgrade head` and the **whole** `pytest` suite against a throwaway Postgres, with coverage gates on `app/domain` and `app/`.

**Backend CI runs every test, database tests included, and needs no secrets** (since 2026-09-23; before that it skipped the 90 database tests). The database tests don't need Supabase itself: `tests/conftest.py` signs its own tokens and fakes Storage, and `db_session` wraps each test in a savepoint that is rolled back. They only need Postgres, so the job runs a `postgres:17.6` service container (production's version, pinned by digest) and nothing ever connects to the live project, on fork PRs either. Two Supabase-specific pieces the migrations rely on are recreated first by `backend/tests/ci/supabase_shim.sql`:

- the `anon` and `authenticated` roles, **with Supabase's default grants on new `public` tables**, so the tables the early migrations create really are exposed and `tests/test_database_security.py` proves the lockdown migrations close them, rather than passing on a database that was never open;
- a minimal `auth.users` (`id`, `email`), which early migrations reference.

A migration that reaches further into Supabase fails CI at the Migrate step; extend the shim. Every migration also runs from an empty database on every PR, which nothing checked before.

Things worth knowing:

- Coverage runs with `concurrency = ["greenlet", "thread"]` (`backend/pyproject.toml`). SQLAlchemy's asyncio layer runs database calls in greenlets, and without it coverage loses a route after its first database `await` (`app/api` read 51–70% instead of 86–100%).
- Two gates: ≥95% on `app/domain`, the home of every invariant (99% now), and ≥90% on all of `app/` (94% when set). What stays uncovered is mostly what tests replace on purpose: the Storage HTTP calls (`app/db/storage.py`) and the production session's commit path (`app/db/session.py`).
- The `integration` marker (`tests/conftest.py::pytest_collection_modifyitems`, automatic for any test using `db_session`) no longer affects CI. It remains so a developer without a database can run `pytest -m "not integration"`.
- Not covered by CI: real Supabase Storage, any difference between the shim and a real Supabase database, and concurrency (the single-session fixture can't drive two connections). Running `pytest` against the real project with a `backend/.env` is still possible and worth doing for changes to migrations or to Supabase-facing code.

## Invariants

1. **Visibility is enforced only in `backend/app/domain/`, on every read path** — lists, search, Tag filters, Glossary, counts, backlinks, notifications, exports, and the Agent API all pass through the same visibility filter before a response is built. No route handler or data‑access query is allowed to return unfiltered content directly to the client (I-01, NFR-01, VR-07).
2. **The frontend never accesses Postgres or Storage directly.** All domain reads and writes go through the backend API, so authorization and visibility logic exist in exactly one place (this document's Auth and Access Model).
3. **A reply can never be stored with a visibility wider than its parent post.** This is enforced in the domain layer when a reply is created or its visibility changed, not only validated client‑side (D-17, VR-04, FR-V6).
4. **The Master is always treated as an implicit Owner** of every Document in their Room, even with no explicit Owner row — any Ownership check must account for this rather than querying the Owner list alone (D-12).
5. **A Room can never end up without a Master or without an Administrator.** The last Master cannot leave or be demoted, and the last Administrator cannot leave, without first designating a successor — enforced as an application‑level check on every membership‑removal and role‑change request, not left to the UI (D-16, FR-R7).
6. **Role and Ownership checks run before any mutation**, and visibility checks run before any content is included in a response — never after (mirrors the corresponding rule in `code-standards.md`).
7. **Every visibility change, Reveal action, role change, and Ownership transfer is written to the AuditLog** in the same transaction as the change itself (VR-08, NFR-06).
